# ZURA-UMKM — Scanning, Tracing, Security Audit & Implementation Plan

**Tanggal:** 05 September 2026
**Tujuan:** Keamanan kode agar lolos pengujian *penetration testing*, efisiensi kode, tracing relasi file frontend, dan implementation plan.

## 1. Ringkasan Proyek

ZURA-UMKM (UMKM Pulse) adalah platform manajemen ritel multi-channel (Shopee, Tokopedia, TikTok Shop, Toko Fisik) berbasis **React 18 + Vite + TypeScript** di frontend, dengan **Firebase** (Auth + Firestore) sebagai backend, dan **Vercel Serverless Function** sebagai proxy AI (xAI/Groq).

### Tech Stack
| Lapisan | Teknologi |
|---------|-----------|
| Frontend | React 18, TypeScript 5.5, Vite 5, React Router 6, TanStack Query 5 |
| Styling | TailwindCSS 3.4, design tokens CSS |

| Export | xlsx, exceljs, html2pdf (custom exportHelpers) |
| Backend | Firebase Auth, Firestore |
| Serverless | Vercel Functions (`/api/ai`) |

## 2. Hasil Scanning Keamanan (Security Audit)

### 🔴 KRITIS (Harus diperbaiki segera untuk lolos pentest)

**C1. API Proxy AI terbuka tanpa autentikasi & rate-limiting**
- **File:** `api/ai.ts`
- **Masalah:** Endpoint `/api/ai` tidak memiliki authentication (tidak memverifikasi Firebase ID token), tidak ada rate limiting, dan menerima parameter `model` dari client tanpa allow-list. Ini menjadikannya **open AI proxy** yang bisa dieksploitasi untuk mencuri kuota billing AI (abuse / cost-spike).
- **Serangan:** Attacker bisa memanggil endpoint ini berkali-kali → tagihan API membengkak; bisa mengganti `model` ke model mahal.
- **Remediasi:** Verifikasi JWT Firebase (`verifyIdToken`) di serverless function; tambah rate limit; allow-list model; batasi ukuran body.

**C2. IDOR (Insecure Direct Object Reference) pada write Firestore**
- **File:** `src/api/client.ts` → `updateProduct` (baris 145-149), `deleteProduct` (151-155), `deleteRecap` (197-201)
- **Masalah:** Write besar dieksekusi berdasarkan **document ID saja tanpa mengecek kepemilikan** (`userId == auth.uid`). Jika aturan Firestore (rules) tidak memvalidasi kepemilikan, user A dapat mengubah/menghapus data user B.
- **Serangan:** Jika attacker mengetahui ID dokumen produk milik korban → bisa modify/delete.
- **Remediasi:** Selalu tambahkan klausa `where('userId', '==', uid)` di data layer **dan** tegakkan kepemilikan di **Firestore Security Rules** (wajib: `request.auth.uid == resource.data.userId` pada update/delete).

**C3. XSS pada Export Helper**
- **File:** `src/utils/exportHelpers.ts`
  - `exportToExcel` (baris 73, 83-84): menyisipkan data user (headers & rows) ke XML Excel via **string interpolation tanpa escaping** → bisa menyuntikkan formula/script XML.
  - `exportToPdfPrint` (baris 112-133): menulis `tableEl.outerHTML` dan `title` langsung via `document.write` tanpa sanitasi → jika `title` atau konten tabel berisi HTML/script berbahaya → **stored XSS** dieksekusi di window print (same-origin).
- **Serangan:** Data yang diimport user (nama produk, saluran, tanggal) yang berisi payload `<script>` akan dieksekusi saat export.
- **Remediasi:** Sanitasi/escape semua data sebelum interpolasi XML & HTML (gunakan lib seperti `xlsx`/`exceljs` yang sudah aman, hindari manual String interpolation; untuk PDF gunakan DOM yang aman bukan `document.write`).

**C4. Secret/API Key**
- **Status:** Sudah ditangani pada commit `fb904d7` — key dipindah ke server-side (`process.env.GROQ_API_KEY` di `api/ai.ts`). `.env` **tidak** ter-track di git (diverifikasi via `git ls-files`). ✅
- **Catatan:** `.env` masih tersimpan di disk lokal berisi `GROK_API_KEY` asli dan konfigurasi Firebase. Pastikan key di server Vercel diset sesuai (environment variable `GROK_API_KEY` atau `XAI_API_KEY`), dan **jangan pernah commit** file `.env`.
- Firebase API key adalah *public-by-design* (aman untuk ekspos di client), tapi pastikan **token autentikasi & aturan Firestore** yang menjadi pengaman utama.

### 🟠 SEDANG

**S1. Eksfiltrasi data bisnis ke LLM**
- **File:** `src/api/grokService.ts`, `src/components/Chatbot.tsx`, `src/pages/AiInsightsPage.tsx`, `src/pages/FinancePage.tsx`
- Data lengkap inventaris (SKU, nama, stok, harga), omzet, unit terjual, dan data finansial dikirim ke API pihak ketiga (Groq/xAI). Tidak ada filter PII, tidak ada consent eksplisit.
- **Remediasi:** Minimalkan data (kirim agregat, bukan detail), tampilkan pemberitahuan privasi, dan jangan kirim field sensitif yang tidak perlu.

**S2. `document.write` dan manipulasi DOM langsung**
- **File:** `src/utils/exportHelpers.ts`
- Penggunaan `document.write` sudah deprecated dan berbahaya. Gunakan `printWindow.document.body.innerHTML` setelah sanitasi, atau cetak elemen DOM yang sudah ada.

**S3. CSP lemah terhadap `'unsafe-inline'`** (`script-src`/`style-src` di `vercel.json`)
- Diperlukan untuk framework, tapi meningkatkan risiko XSS. Pertimbangkan `nonce`/`hash` bila memungkinkan.

**S4. Data kelola localStorage berlebihan**
- Banyak data disimpan duplikat di `localStorage` (kategori custom, SOP, profil, beban operasional). Risiko: data basi, inkonsistensi, dan potensi manipulasi client-side.

**S5. Debug code dibiarkan**
- **File:** `src/pages/DashboardPage.tsx` baris 58-60: `console.log` data mentah recaps saat load — membocorkan data ke console (minor) dan menambah overhead.

### 🟢 RENDAH / NOTE
- `src/config/firebase.ts` baris 17: `googleProvider` diekspor tapi tidak dipakai (LoginPage membuat instance sendiri) — dead code.
- Komentar stale di `src/utils/tokens.ts` (nama "DEEP_TEAL" tapi nilai biru `#3B82F6`).
- Header `Access-Control-Allow-Origin` statis di `vercel.json` (fine untuk single-origin, tapi perlu review jika multi-domain).

### ✅ Sudah Bagus
- `ProtectedRoute` yang memanfaatkan `onAuthStateChanged` untuk gating rute privat (client-side). **Catatan:** ini hanya UX guard — keamanan sesungguhnya harus dari Firestore security rules.
- Re-authentication sebelum change email/password/delete akun di `ProfilePage.tsx`.
- API key tidak ada di browser; diproksi via serverless.
- Security headers di `vercel.json` (X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy, CSP).
- Error handling & feedback toast di mayoritas fitur.

## 3. Hasil Tracing & Analisis Efisiensi Kode

### 3.1 Skema I/O Client.ts (Firestore data layer)

`src/api/client.ts` adalah satu-satunya lapisan akses data. Fungsi utamanya:

| Fungsi | Collection | Operasi | Keamanan kepemilikan |
|--------|-----------|---------|----------------------|
| `fetchUserProfile` | `users/<uid>` | read (by uid doc) | ✅ (by uid) |
| `updateUserProfile` | `users` | write | ⚠️ payload userId |
| `fetchUserSettings` | `settings/<uid>` | read | ✅ |
| `updateUserSettings` | `settings` | write | ⚠️ payload userId |
| `fetchInventory` | `products` | read where userId==uid | ✅ |
| `addProduct` | `products` | create (userId di-set client) | ⚠️ trust client |
| `updateProduct` | `products/<id>` | write **tanpa cek owner** | ❌ IDOR |
| `deleteProduct` | `products/<id>` | delete **tanpa cek owner** | ❌ IDOR |
| `fetchRecaps` | `recaps` | read where userId==uid | ✅ |
| `addRecap` | `recaps` | create | ⚠️ |
| `deleteRecap` | `recaps/<id>` | delete **tanpa cek owner** | ❌ IDOR |
| `fetchCustomers` | `customers` | read | ✅ |
| `fetchTransactions` | `transactions` | read | ✅ |
| `fetchKpiSummary` | agregat | read | ✅ |

### 3.2 Schema Drift (Bug efisiensi/kebenaran)

- **`types/index.ts`** mendefinisikan `KpiSummaryResponse` berisi `todayRevenue`, `todayTransactions`, `bestSellerProduct`, `stockAlerts`, **tetapi** `fetchKpiSummary()` di `client.ts` mengembalikan `{ totalRevenue, totalOrders, totalCustomers, activeProducts }`. → **Mismatch tipe** antara kontrak dan implementasi.
- Hook `useSalesChart.ts`, `useRestockPlan.ts`, `useInventory.ts` mendeklarasikan tipe `SalesChartResponse`, `RestockPlanResponse`, `InventoryResponse` tetapi `client.ts` **tidak memiliki** `fetchSalesChart`/`fetchRestockPlan` dan bentuk `fetchInventory` (return array) tidak cocok dengan `InventoryResponse.products`. → Risiko bug runtime & kebingungan kontrak.
- **Catatan:** `npx tsc --noEmit` lolos tanpa error karena banyak penggunaan `as any` / loosening, menyembunyikan drift tersebut.

### 3.3 Efisiensi — Pengulangan Query & State

- Query key `['recaps']`, `['inventory']`, `['customers']` di-*share* antar page. Ini **baik** untuk cache TanStack Query, tapi setiap page masih menjalankan queryFn sendiri dengan logika duplikat (`Array.isArray(res) ? res : []`) → **duplikasi kode** di DashboardPage, SalesRecapPage, FinancePage, AiInsightsPage, Chatbot, InventoryPage (sekitar 6x).
- **Rekomendasi:** Buat hook kustom `useRecaps()`, `useProducts()`, `useCustomers()` yang membungkus normalisasi array agar single source of truth dan mengurangi duplikasi.
- `DashboardPage.tsx` (~1078 baris) dan `SalesRecapPage.tsx` (~1334 baris) serta `ProfilePage.tsx` (~1026 baris) sangat besar — menduplikasi UI desktop/mobile. **Rekomendasi:** pecah menjadi komponen kecil, pisahkan logika bisnis ke hooks/util agar mudah diuji & efisien.
- **Fakta keras:** margin laba `totalProfit = Math.round(totalOmzet * 0.428)` di DashboardPage (baris 166) adalah **angka flat/hard-coded** (42.8%), bukan kalkulasi riil dari HPP. Ini bukan bug keamanan tapi **kesalahan akurasi bisnis** yang perlu diganti kalkulasi nyata.
- `localStorage.clear()` dipanggil di LoginPage & NavBar logout — biasanya OK, tapi pastikan tidak menghapus data penting user.

### 3.4 Alur Data (Data Flow Trace)

```
[LoginPage] -> Firebase Auth (signIn/popup)
      ↓ (user)
[ProtectedRoute] onAuthStateChanged → gate /dashboard, /ai-insights, /rekap, /inventory, /finance, /profile
      ↓
[AppShell] (NavBar + Outlet + Chatbot)
      ↓
Pages memuat data via TanStack Query → src/api/client.ts → Firestore (where userId==uid)
      ↓
AI: Chatbot/AiInsights/Finance → src/api/grokService.ts → POST /api/ai (Vercel) → api.groq.com/x.ai (server-side key)
```

## 5. Implementation Plan (Remediasi & Optimasi)

### Fase 1 — Hardening Keamanan (Paling Kritis, ≥ Prioritas Tinggi)
1. **`api/ai.ts` — autentikasi & proteksi proxy AI**
   - Verifikasi Firebase ID Token (via Admin SDK) sebelum meneruskan request.
   - Tambah rate limiting (misal: per user/sesi).
   - Allow-list `model` (default `llama-3.3-70b-versatile`).
   - Batasi ukuran body request (`JSON.stringify(messages)` cap).
2. **Firestore Security Rules — enforce kepemilikan**
   - Rules wajib: `allow write: if request.auth != null && request.auth.uid == request.resource.data.userId`
   - `allow update, delete: if request.auth.uid == resource.data.userId`
   - `allow read: if request.auth != null && request.auth.uid == resource.data.userId`
3. **`exportHelpers.ts` — sanitasi XSS**
   - Ganti manual XML string interpolation dengan `exceljs` (sudah ada di deps) untuk export Excel.
   - Untuk PDF: bangun DOM baru dengan `innerHTML` **ter-sanitasi** (escape `<`, `>`, `&`, `"`, `'`), hindari `document.write`.
   - Sanitasi semua nilai user sebelum dimasukkan ke dokumen.
4. **IDOR di `client.ts`**
   - `updateProduct`/`deleteProduct`/`deleteRecap`: tambahkan pengecekan kepemilikan di data layer (query by id + validasi `where('userId','==',uid)`) sebagai *defense in depth*.
5. **Privasi data AI**
   - Minimalkan data yang dikirim ke LLM; tampilkan pemberitahuan; hanya kirim agregat/PII yang diperlukan.

### Fase 2 — Perbaikan Kontrak & Kebenaran Kode
6. **Sinkronkan schema `types/index.ts` dengan implementasi `client.ts`**
   - Samakan `KpiSummaryResponse` dengan return aktual, atau perbaiki `fetchKpiSummary` untuk memenuhi kontrak.
   - Hapus/resolve hook yang memanggil fungsi tidak ada (`useSalesChart`, `useRestockPlan`) — implementasikan `fetchSalesChart`/`fetchRestockPlan` atau hapus hook.
7. **Perbaiki margin laba hard-coded**
   - Ganti `* 0.428` di `DashboardPage.tsx:166` dengan kalkulasi dari HPP riil (sum `buyPrice * qty`).

### Fase 3 — Refactor & Efisiensi
8. **Buat hook kustom shared**: `useRecaps()`, `useProducts()`, `useCustomers()` — menghapus duplikasi normalisasi array (±6 tempat).
9. **Pecah page raksasa** (DashboardPage 1078, SalesRecapPage 1334, ProfilePage 1026) menjadi komponen/hook modular.
10. **Hapus debug log** di `DashboardPage.tsx:58-60`.
11. **Hapus dead code**: `googleProvider` di `firebase.ts:17`, perbaiki token kronis.
12. **Konsolidasi localStorage** — kurangi duplikasi data (kategori, SOP, profil, beban operasional) supaya efisien & konsisten.

### Fase 4 — Verifikasi & Uji
13. Tambahkan unit test untuk fungsi sanitasi export.
14. Jalankan `npm run test` (Vitest) & buat test baru untuk data layer (ownership check).
15. Review `vercel.json`:
    - Pertimbangkan nonce/hash pada CSP menggantikan `'unsafe-inline'`.
    - Tinjau `Access-Control-Allow-Origin` statis.
16. Jalankan `npm run build` untuk memastikan bundle efisien & sukses.
